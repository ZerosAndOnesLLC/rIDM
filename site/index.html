An identity server you run yourself, written in Rust.

rIDM is an open-source OpenID Connect and SAML 2.0 provider for many tenants at once, with MFA, passkeys, brokering to the providers and directories your users already have, and an admin console and account console in the same image. One container, Postgres and Valkey.

Get started Source on GitHub

Version 0.2.0 is the first published release, licensed MIT. Until 1.0 a minor version may change compatibility, and the changelog says how.

Quick start from a clone of the repository 
# encrypts secrets at rest; keep it safe
$ export MASTER_KEY=$(openssl rand -hex 32)
$ docker compose -f deploy/docker-compose.yml \
    --profile dev up -d
$ curl http://localhost:8080/readyz
The dev profile seeds a first administrator in the master tenant and adds Mailpit to catch outbound mail. The admin console is at localhost:8080/console/. Run rIDM locally walks through it, and deployment covers production.

https://id.example.com/t/acme

Every tenant is its own issuer. Its own signing keys, users, clients, policies, branding and administrators. A token from one tenant is never valid in another, because the iss claim differs and its key is not in the set the relying party fetched.

Isolated in Postgres, not just in code. Every tenant-scoped table has a forced row level security policy bound per transaction, and foreign keys carry the tenant id. A query that forgets its WHERE returns nothing from other tenants.

Slugs, or your own domain. staging and production side by side, one tenant per customer, or a custom domain so users keep the login hostname they know. Tenants and issuers explains the model.

Built to be run, not rented

rIDM is for operators who want an identity provider on their own infrastructure, and for developers who want standard OAuth 2.0 and OpenID Connect to integrate against, without a vendor SDK.

Multi-tenant from the first migration

Tenants are not a plugin. Every tenant-scoped table leads its indexes with tenant_id, and Postgres itself hides other tenants' rows from each transaction.

Standards, and only the safe ones

Authorization code with PKCE, PAR, DPoP, mutual TLS, CIBA, FAPI 2.0 and more. No implicit flow, no hybrid flow, no password grant, no plain PKCE: a misconfigured client cannot fall back to a weaker one.

One image

The container compiles the sign-in pages, the admin console and the account console into the server and serves them on its own origin. Nothing else to host; the same export can also go on a CDN.

Configuration as code

A tenant exports to one JSON document and imports idempotently, with a diff first. Keep it in version control and apply it to any deployment. How it works.

MFA, passkeys and adaptive sign-in

TOTP, email and SMS codes, WebAuthn passkeys as the first factor or the second, recovery codes, policy per tenant and per role, step-up per client, and risk scoring on new devices, new countries, impossible travel and velocity.

Keys where you want them

Per-tenant signing keys with rotation. The master key that encrypts secrets at rest can live in the environment, a PKCS#11 HSM, AWS KMS, HashiCorp Vault or OpenBao, Google Cloud KMS or Azure Key Vault. Key custody.

Data residency

One deployment, regional databases. A tenant created in eu keeps its users, credentials, sessions, keys and audit log in the eu database and nowhere else. Data residency.

Built for scale

Stateless nodes, cache-first reads with invalidation over Valkey pub/sub, short-lived JWTs, Valkey Sentinel or Cluster, Postgres read replicas, Prometheus metrics and OpenTelemetry traces. Scaling.

Three moving parts

A deployment is ridm-api, Postgres and Valkey. Nodes keep nothing another node needs, so any node serves any request and there are no sticky sessions. Add nodes behind any proxy or load balancer.

Nothing sticky. A session, a login flow half-way through, an authorization code or a rate-limit count lives in Valkey or Postgres, never on a node.

Cache first. Each node caches the hottest read-mostly objects for about fifteen seconds; a write evicts them on every node through a pub/sub channel.

Configured by environment. The same image runs everywhere. PUBLIC_URL fixes every issuer, and one master key, from the environment or a KMS, encrypts what is at rest.

Observable. Prometheus metrics, OpenTelemetry traces, structured logs, and a per-tenant SHA-256 hash chain over the audit log that ridm audit verify checks. Deployment overview.

Protect a Rust API in a few lines

The ridm-auth crate validates rIDM access tokens in your own axum service. Any other language uses an ordinary OIDC or JWT library against the tenant's discovery document.

One Validator per issuer holds the key-set cache; a Guard protects a route subtree and refuses anything short of what it asks for. Every refusal is an RFC 6750 response with a WWW-Authenticate challenge, and your handlers write none of it.

What it checks on every request

  • the signature, against the issuer's JWKS, refetched when a token names an unknown kid
  • JOSE typ is at+jwt, so an ID token cannot be spent as an access token
  • iss, aud, exp and nbf
  • a DPoP-bound token is refused rather than downgraded
  • the scopes, permissions and roles the guard asked for
401no token, or one that is expired, mis-signed or minted for another API
403a valid token without the permission the route requires
200the verified claims are handed to your handler

Protect a Rust API with ridm-auth is the full walkthrough, and examples/axum-api is the runnable version.

src/main.rs
use ridm_auth::Validator;
use ridm_auth::axum::{Guard, RidmClaims, guard};

// One validator for the whole process: it holds the key-set cache.
let validator: Arc<Validator> = Validator::builder(&issuer)
    .audience(&audience)
    .discover()
    .await?
    .shared();

let read = Router::new()
    .route("/invoices", get(list_invoices))
    .route_layer(from_fn_with_state(
        Guard::new(validator.clone())
            .permission("invoices:read")
            .realm("invoices"),
        guard,
    ));

let app = Router::new()
    .route("/whoami", get(whoami)) // any valid token
    .merge(read)
    .with_state(validator);

async fn list_invoices(RidmClaims(claims): RidmClaims) -> Json<Value> {
    Json(json!({ "invoices": [], "for": claims.sub }))
}

Bare metal, docker-compose, Kubernetes or any cloud. No provider-specific dependency in the default build; email over SMTP or an HTTP API, and secrets encrypted with a key you hold.

Releases

Signed, so you can check what you run

Every release is built from a v* tag by the release workflow and signed with Sigstore keyless signing. Verification names that workflow and GitHub's token issuer, so a check that fails means the artifact was not built there, or was changed since. Releases and verification.

IDENTITY='^https://github.com/ZerosAndOnesLLC/rIDM/\.github/workflows/release\.yml@refs/tags/v'
cosign verify ghcr.io/zerosandonesllc/ridm:0.2.0 \
  --certificate-identity-regexp "$IDENTITY" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

From Keycloak

A realm becomes a tenant. Clients keep their client_id and redirect URIs; a bearer-only client becomes a resource server, so the aud your API checks can stay the same.

  • Realm roles, client roles, groups and client scopes have direct counterparts
  • Users import in bulk with their password hashes, verified in the original format at first sign-in and then re-hashed with argon2id
  • Secrets, signing keys and sessions do not carry over; users sign in once more

From Auth0

An Auth0 tenant becomes an rIDM tenant. Applications become clients of the matching type, and an API becomes a resource server with its identifier unchanged.

  • API permissions become permissions and scopes on the resource server
  • The user export, with hashes, converts to bulk-import rows
  • Rules and Actions have no direct equivalent; the guide says what replaces each common one
